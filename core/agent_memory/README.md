# agent_memory/ — 记忆归档（Agent Memory Archive）

> **本目录是本项目 Agent 记忆系统的规范定义。** 任何 Agent 在本目录下新增内容前，先读完本文件。
> 面向新会话的入口在项目根 `CLAUDE.md`；本文件回答的是「**放什么、放哪、什么时候更新**」。

---

## 一、分层链路（渐进披露）

```
CLAUDE.md（内核 / tier-0）        自动加载；只写协议，不写知识
    ↓ 需要更多上下文
BOOT.md（状态快照 / tier-1）      当前状态 + 任务→文件路由表
    ↓ 需要完整细节
current_state.md（手册 / tier-2） 完整项目知识 + 索引
    ↓ 需要历史背景
session_logs/（历史 / tier-3）    逐次会话记录，纯追加
plans/ prompts/                   计划 / 一次性任务简报
```

> 注：`plans/` 在内核的启动序列里（第 6 层），**`prompts/` 不在**——它是**派活**给新 Agent 时
> 才读的，不参与每会话的启动链路。两份文档对同一结构的层数表述不同时，以内核为准。

**设计原则**：最小化常驻 Prompt 文字量。每一层只包含「下一层需要时才会读取」的信息。
判断一条信息该放哪层，问自己：**「每次会话都必须知道吗？」** 否则往下沉一层。

## 二、文件约定

| 位置 | 角色 | 何时读 | 何时写 |
|---|---|---|---|
| `../CLAUDE.md` | 内核 | 每次自动 | 目标/阶段/风格变化时 |
| `BOOT.md` | 状态快照 + 路由表 | 多数任务 | 每次会话结束 |
| `current_state.md` | 完整手册 + 索引 | 需要细节时 | 结构变化时 |
| `session_logs/` | 历史 | 需要背景时 | **每次会话结束** |
| `plans/` | 计划 | 需要规划时 | 立项 / 结项 |
| `prompts/` | 一次性任务简报 | 派活给新 Agent 时 | 派活前 |

**命名约定**
- session log：`session_YYYYMMDD_<slug>.md`（date 为会话主日期，非文件修改时间；slug 用 snake_case 描述**活动**）
- plan：`YYYY-MM-DD-<kebab-slug>.md`
- prompt：**两种**，靠有无日期区分
  - `YYYY-MM-DD-<kebab-slug>.md` —— **一次性简报**：为某次具体任务写的，**发出去就不再修改**（要改就新写一份，让旧的留作决策痕迹）
  - `<kebab-slug>.md`（无日期）—— **常驻可复用的启动指令**：每次都用的那种，会随项目演进而更新
  > 区分这两者很重要：给一份"改了也没关系"的常驻指令套上日期，会让后人以为那是某天的存档而不敢动。
- 专题文档：`<kebab-slug>.md`（放本目录下）

## 三、四条硬约定

1. **状态快照必须带陈旧度信号。** `BOOT.md` 和 `current_state.md` 顶部都要有陈旧度信号：
   `BOOT.md` 写 `**Updated**: YYYY-MM-DD`，`current_state.md` 写 `**最后更新**: YYYY-MM-DD`（两者都带日期即可，校验脚本两个键都认）。
   没有日期的状态文件等于没有状态；但**脚手架初始化时写入的日期不算**——那时的日期只说明「文件是刚生成的」，
   所以两个文件都带一句「脚手架初始化」标注，**首个产出了东西的会话**后必须用真实日期替换它。
   ⚠️ 「产出了东西」= 有结论、有产物、有决定。**只问了几句、没有产出的会话不算**——
   那种会话按内核 `CLAUDE.md` 的规定本来就不写 session log；为了"把日期换成真实值"而去填
   `BOOT.md` 的状态表，就是编造。没有内容可填时，保留「脚手架初始化」标注才是正确的。
2. **索引放在手册末尾，历史目录纯追加。** `session_logs/` 内不放索引文件；索引统一在 `current_state.md` 的「会话日志索引」一节。新增日志后**必须**补索引行。
3. **计划必须有生命周期。** `plans/` 下每份计划 frontmatter 带 `status: active | done | superseded`。立新计划时把被取代的旧计划标 `superseded` 并填 `superseded_by`。**任何时刻 `active` 至多一份。**
4. **产物清单是找回东西的唯一线索。** 每份 session log 必须有一张「产物清单」表（`文件 | 说明`），列出本次产生的全部路径。后续会话靠它检索。

## 四、扩展点（预先授权）

执行新任务时，若发现 `current_state.md` 没有覆盖所需领域，**可以直接在本目录下新建专题文档**
（例如 `gpu_setup.md`、`data_pipeline.md`），并**必须**在 `current_state.md` 末尾的「专题文档索引」里加一行链接。

> ⚠️ **前提：项目已有真实内容。** 空脚手架阶段「`current_state.md` 没有覆盖所需领域」**恒为真**——
> 这时不要新建专题文档，那只会产出一份空洞的、看起来像知识的文件。停下来问用户
> 「这个项目要做什么」。判断依据见内核 `CLAUDE.md` 的 Boot Sequence §①。

这是本系统唯一的扩展方式——不要再新增顶层目录。

## 五、与 Claude Code 原生记忆的关系

Claude Code 在 `~/.claude/projects/<slug>/memory/` 另有一套自动记忆（索引 + frontmatter 原子条目）。

**边界规则**：
- **项目状态、叙事、计划、实验记录 → 一律写本项目 `agent_memory/`**（随 git 走，换机器不丢）
- **只有「换个项目也用得上」的事实**（如本机环境的坑、CLI 怪癖）→ 才额外写原生记忆
- 原生记忆**不进 git**，不要把它当作项目知识的唯一存放处

## 六、更新检查表（会话结束时逐项过）

> ⚠️ **仅当本次会话真的产生了工作成果时才走这张表。** 纯问答、空脚手架上的确认，
> 一律不写 session log——「没有产出」是合法状态，硬凑「核心结果」表格比留空更糟。

- [ ] 写 session log（含产物清单表）
- [ ] 更新 `BOOT.md` 的 `**Updated**` 日期与状态表
- [ ] 在 `current_state.md` 的会话日志索引补一行
- [ ] 若本会话有结论推翻了旧结论 → 更新或标注旧文档
- [ ] 若产生了新专题文档 → 登记到索引
- [ ] 若计划状态变化 → 更新 `plans/` 的 frontmatter
