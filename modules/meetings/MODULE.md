# modules/meetings — 组会与论文阅读记录

> 本模块是 `core/agent_memory/` 的**场景增量**，提供两类记录的模板。
> 核心回答「记忆放哪」；本模块回答「**组会和论文阅读该长什么样**」。

---

## 一、两类记录，两种用途

| 模板 | 记什么 | 核心特征 |
|---|---|---|
| `_TEMPLATE-paper-note.md` | 论文的**结构性转写** | 按论文自身章节编号；转写与批注分离 |
| `_TEMPLATE-advisor-meeting.md` | 组会 / 导师讨论 | 按 slides 编号；**带行动项表** |

**共同原则**：**结构与来源绑定**。论文笔记跟着论文的节号走，组会记录跟着 slides 的编号走。这样日后任何一条记录都能回溯到原始材料的具体位置——「论文 §3.2 说过 X」和「第三张 slide 上写的 Y」都是可验证的，而「我记得论文里提过 X」不是。

---

## 二、论文笔记：为什么转写与批注必须分开

`_TEMPLATE-paper-note.md` 是**结构性转写（structural transcription）**，不是「我的收获/总结」。它按论文自己的编号组织：Abstract / 1 Introduction / 2 Related Work / 3 Proposed Method / 4 Experiments / 5 Conclusion / References / Appendix。

**为什么不用「我的总结」形式**：总结会把论文的主张与你的理解**熔在一起**，从此再也分不开。具体代价：

| 场景 | 用总结形式 | 用转写 + 批注分离 |
|---|---|---|
| 引用论文的论断 | 无法确定这是论文说的还是你推断的 | 转写区可逐句回溯 |
| 复现失败，怀疑论文有坑 | 只记得「它说效果好」 | 能查原文的 hedge 词与实验条件 |
| 与他人讨论 | 转述失真，且不自知 | 可对照原文 |
| 论文之间交叉对照 | 各自的总结口径不同，无法比较 | 结构一致，可逐节对比 |
| 半年后回看 | 忘了哪些是自己的判断 | 章节目录即原文结构 |

**关键约束**（写在模板里，此处复述）：

1. **转写区只陈述论文说了什么**，不做评价、不做推荐。
2. **不抹掉 hedge 词**。「may」「suggests」「we hypothesize」决定论断强度；抹掉就变成了论文没说过的话。
3. **数字原样转写**，不四舍五入、不换算单位。这些数字日后是复现的对照基准。
4. **`## 我的批注` 放在文件末尾**，与转写之间有明确分隔，且开头标注「以下全部是读者判断」。

> 分隔不是为了形式整洁，是为了**可归因**。你必须在任何时候都能回答：这句话是论文的主张，还是我的读法。

## 三、组会记录：行动项表是最高价值补充

`_TEMPLATE-advisor-meeting.md` 沿用 slide 导出的形态：编号的一级章节（`上次回顾` / `本次实验设置` / `本次结果` / `待研究问题` / `导师建议` / `后续计划`），每节带 `### Notes:` 占位。

**原组会模板缺少「行动项表」——这是最该补的一块。** 理由：

- 组会记录的价值不在于「开了什么会」，而在于「**会后谁做什么**」。没有行动项表，记录退化为一份无人使用的文档。
- 分散在「导师建议」和「后续计划」里的口头任务，**会漏**。集中成表才能逐行核对。
- 下周组会想知道「上周说的做完了吗」，只需扫一遍状态列，而不是重读全文。
- 期限是**判定完成与否的前提**。「尽快」「下周」不是期限。

本模板的行动项表字段（见模板 §行动项）：

| 字段 | 规则 |
|---|---|
| 事项 | 动词开头，**可判定完成**——写「跑通 X 并得到 n=3 的 mean±std」，不写「研究 X」 |
| 负责人 | 具体到人 |
| 期限 | 必须有日期 |
| 状态 | `todo` / `doing` / `done` / `dropped` |
| 对应来源 | 指回本文件章节，保证可追溯 |

**其他设计要点**：

- **§2.5 实验组设置**要求写明组间是否只差一个变量、重复数 N——这是判据，不是格式。
- **§3.3 当前结论的局限性**：主动列局限，比等被指出更有效，也防止结论被过度外推。
- **§4 待研究问题**：每个问题必须写「**如何验证**」。只写问题不写验证手段，下次组会还会停在同一个问题上。
- **§6 计划**：Plan A/B/C 每个都要有**失败判据**——什么情况下放弃并切到下一个。

## 四、命名约定

### 4.1 论文笔记

```
meetings/
  {{PaperName}}.md              # 模式：论文的方法名 / 简称，保持与代码仓库名一致
  {{MethodName}}.md
```

| 规则 | 说明 |
|---|---|
| **用方法名，不用标题全称** | `ResNet.md` 而非 `ResNet-Deep-Residual-Learning-for-Image-Recognition.md`。文件名是**检索键**，短且唯一即可 |
| 大小写保持方法名的官方写法 | `ResNet.md`、`BERT.md`、`ViT.md` |
| 同名冲突时加年份或作者 | `{{MethodName}}-{{YEAR}}.md` |
| 不建子目录 | 论文笔记平铺；靠 frontmatter 的 `relevance` 与 `read_date` 检索 |

**frontmatter 字段**（模板已含）：`paper` / `venue` / `year` / `url` / `code` / `read_date` / `relevance`。

> `read_date` 是**你读它的日期**，不是发表年份——两者都重要，所以分开放。

### 4.2 组会记录

```
meetings/
  2026-08-09.md                 # 模式：YYYY-MM-DD.md
  Week-{{N}}-导师建议.txt        # 导师本人建议（纯文本）
  Week-{{N}}-导师他人建议.txt    # 其他参会者转述的意见（纯文本）
```

| 规则 | 说明 |
|---|---|
| **组会用 `YYYY-MM-DD.md`** | 日期即身份；按文件名排序 = 时间线排序 |
| **周次写进 frontmatter 的 `week`**，不进文件名 | 周次会因学期/项目重置，日期不会 |
| 一次组会一天多个议题 → 仍是一个文件 | 议题写在 frontmatter 的 `topic` 与正文分节 |
| 论文笔记用方法名，组会用日期 | 两类前缀区分明显，`ls` 时一眼可辨 |

### 4.3 导师建议的纯文本惯例 ⭐

**源项目中，导师建议是用自由格式 `.txt` 记录的**，而不是结构化模板：

```
Week-{{N}}-导师建议.txt          # 导师本人的建议
Week-{{N}}-导师他人建议.txt      # 他人转述 / 其他参会者的意见
```

**本模块建议保留这个惯例与这个分离。** 理由：

| 点 | 说明 |
|---|---|
| **纯文本反而合适** | 导师建议是**转瞬的、口语的、未结构化的**。当场用模板填表会打断听讲，且会因「格式不对」而漏记内容 |
| **分离是核心** | 「导师说了什么」和「别人说导师说了什么」**可靠性不同**。混淆后，一条二手转述会被当成导师的明确指示执行，且无从察觉 |
| **纯文本好追加** | 会上边听边追加，事后不重排格式 |
| **结构化的工作交给 md** | 会后再把要点摘进 `_TEMPLATE-advisor-meeting.md` 的 §5 导师建议 与 §行动项 |

**两个文件的边界**：

| 文件 | 只放 |
|---|---|
| `Week-N-导师建议.txt` | 导师**本人**当面/书面给出的建议 |
| `Week-N-导师他人建议.txt` | 他人转述的导师意见、其他老师/同学的建议、听来的经验 |

**录入规则**：
- 建议的**归属不确定时**，放「他人建议」，并标注来源。
- `.txt` 里的内容**不做修饰**——保留口语原样，包括不确定的措辞（「可能可以试试」）。
- 会后 24h 内把要点摘进当周 md 的 §5 与 §行动项；**摘录时保留归属**。

> 不要在 `.txt` 里做取舍：**「记下来」和「判断值不值得做」是两件事**，前者在会中做，后者在会后做。

## 五、与 core 的接口

| 产出 | 归档位置 |
|---|---|
| 论文笔记 | `meetings/{{MethodName}}.md` |
| 组会记录 | `meetings/YYYY-MM-DD.md` |
| 组会中产生的实验计划 | `agent_memory/plans/YYYY-MM-DD-<slug>.md`（带 `status` frontmatter） |
| 组会中得到的实验数值 | `agent_memory/session_logs/session_YYYYMMDD_*.md` |

> 上表右列写的是**落地后**的路径（项目根为基准）。本节标题里的「与 core 的接口」指
> 「与内核 `agent_memory/` 的接口」——路径里没有 `core:` 这种前缀，别去项目里找它。
| 论文中的关键参数 | `modules/reproduction/docs/reproduction_protocol.md` §3 参数对照表 |

> **论文笔记 → 复现方案的接口**：读论文时在 §3.3 实现细节记下的参数表，可直接抄进复现方案的逐条对照表。这是本模块与 `modules/reproduction/` 的接合点。

## 六、使用检查表

**论文笔记**：
- [ ] frontmatter 七个字段齐全，`relevance` 写的是「为什么读它」而不是「它讲了什么」
- [ ] 章节编号与论文一致
- [ ] 关键论断标注了原文位置，hedge 词保留
- [ ] 论文未说明的项已列进 §3.4
- [ ] `## 我的批注` 在文件末尾且与转写有明确分隔

**组会记录**：
- [ ] frontmatter 四个字段齐全
- [ ] §1 回应了上期的问题（未回应则写明原因）
- [ ] §3.3 主动列了局限
- [ ] §4 每个问题都有「如何验证」
- [ ] §5 只含导师本人建议；他人意见在单独的 `.txt`
- [ ] §行动项 每行都有负责人 + **日期**；事项可判定完成
- [ ] 上次记录中的 `todo` 项已更新状态
