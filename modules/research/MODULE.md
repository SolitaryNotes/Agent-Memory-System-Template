# modules/research — 科研项目层（背景文档 + 实验产物规范）

> 给"做实验、出图、写论文"的项目补充内核之外的一层：**背景知识如何自包含地传递**、
> **实验产物如何不靠记忆就能被追溯**、**图与脚本如何不漂移**。
> 内核（`core/`）管的是"跨会话的记忆"；本模块管的是"跨会话、跨机器、跨协作者的科研事实"。

## 何时该引入本模块

引入，如果项目满足**任意两条**：

- 有连续的实验序列（同一批变量反复跑，结果要横向比较）
- 会把实验打包丢到远端/云端跑，需要另一台机器上的 Agent 照做
- 需要把课题背景反复讲给新的 AI 协作者（网页端 / 云端 Agent / 换机器）
- 会产出图，且图要区分"中间产物"与"定稿"

**不要引入**，如果只是脚本集合、一次性分析、或没有"结果需要被别人复现"的需求——
本模块的规矩（命名序号、run.json、镜像目录）是**协作成本**，单次任务付不起。

## 本模块假设什么

- Python + matplotlib 的绘图流程；仓库根下有 `configs/`、`experiments/`、`results/`、`figures/`
- 实验是"跑一次产出一个目录"的形态（训练、评测、批量扫描都适用）
- 使用者能接受一条硬规矩：**新图默认进 `exploratory/`，只有人明确授权才进 `curated/`**

| 路径 | 作用 |

## 一、图的产出等级：默认 `exploratory`

```
experiments/plot/{exploratory,curated}/{NN}-{name}.py
figures/{exploratory,curated}/{NN}-{name}/          ← 与脚本同名
```

- `exploratory/` — Agent 生成的中间产物。**新图一律先落这里**，不入库。
- `curated/` — 人工打磨过、用于组会/论文的定稿图，入库。

**只有人明确说"这张图转正式"才能搬进 `curated/`。** Agent 不得自行提升：定稿图代表
对外承诺，一张没经人看过的图混进 `figures/curated/`，会直接出现在幻灯片里。

> 提升是**成对操作**：脚本和图目录必须同时移动（`figure_dir()` 会拦住只改一边的情况）。

## 二、命名规则 `{NN}-{kebab-name}`，以及为什么要用 checker 强制

- `NN`：两位序号，决定文件列表里的排序；**必须严格顺序、不得复用**
- `kebab-name`：这段实验/这张图在做什么，用连字符小写

新建前先列 `experiments/plot/{exploratory,curated}/`，取 `max(NN) + 1`。

**为什么不能靠自觉**（真实事故）：

1. **重复序号**：一个新 plot 被起名 `05-q2-clustering`，而 `05-...` 已存在 → 两个 `05`，
   列表排序失去意义，引用"05 那张图"时指向不明。
2. **孤儿图目录**：脚本被改名/删除，`figures/` 下的同名目录留着没人管 → 目录里是过期图，
   下次有人打开它会以为是最新结果。

所以本模块把规则做成**可执行的检查**，而不是文档里的君子协定：

- `figure_dir(tier, name)` 在图上**自动按调用方脚本文件名命名目录**，杜绝手写目录名漂移
- 脚本在 `exploratory/` 却要往 `curated/` 写 → 直接抛错（强制成对迁移）
- 传入的 `name` 与脚本名不一致 → 直接抛错

> 这两项**静态扫描**（`NN` 是否唯一、每个脚本是否有对应图目录）由随内核一起落地的
> `tools/check_conventions.py` 承担（`plot_numbering` 与 `mirror_rule` 两项）。本模块的
> `common.py` 只保证"运行时不会写错"——**不要在项目里另写一份静态检查**，两份规则必然漂移。

## 三、镜像规则（mirror rule）

```
experiments/plot/{category}/{name}.py   →   figures/{category}/{name}/
```

脚本与图目录 **1:1 同名**。看到一张图就知道是哪个脚本产的，改脚本就知道图在哪。
新建脚本要建同名目录，重命名要成对重命名。

## 四、`run.json`：让结果目录自己说清自己是谁

每个 run 目录放一份 `run.json`（schema 见 `run.schema.json`），必填 6 项：
`run_id` / `started_at` / `config` / `git_commit` / `seed` / `note`。

**它解决的问题**（真实事故）：某项目的结果目录里同时躺着 `results/exp/` 和
`results/exp_30ep/`，两者的差别**只能靠文件夹名猜**——里面没有一处记录 epoch 数，
`config` 也没有留档。半年后要复现"exp 到底是 50ep 还是 100ep"时，只能翻聊天记录。
更糟的是，这个差别会实质影响结论：拿 30ep 的曲线去比 100ep 的曲线，横轴都不是一回事。

三条要点：

1. **`config` 存"解析后的完整配置"**，不是只存被 CLI 显式改过的那几个参数。
   写原始输入等于没写——三个月后没人记得当时的默认值是多少。
2. **`run_id` 与目录名一致**，格式 `{YYYYMMDD}-{HHMM}-{kebab-name}`，
   名字里写实验意图（`20260822-1430-lr-warmup-sweep-seed0`），而不是 `run1`。
3. **`seed: null` 是有意义的**：表示"确定性实验、不涉及随机性"，与"忘了填"不同，
   所以它是必填字段但允许 `null`。

### 为什么**不**标准化 `metrics.csv` 的列名

这是刻意的克制。统一列名看起来更整齐，但会立刻逼出一串问题：不同任务的指标根本不同
（回归 MSE / 聚类 ARI / 分类 Acc）、同一指标有多个口径（pooled vs per-dataset）、
有人只想加一列诊断量——每加一种情况，schema 就得改一次，最后要么有人绕过它直接写自由列，
要么为了合规而把真实指标塞进错误的列里。**收益（整齐）远小于成本（僵化 + 绕过）。**

所以本系统只在**一处**设硬约束：`run.json` 的六个必填字段——因为那是唯一"缺失后
就无法追溯、且事后补不回来"的信息。指标 CSV 的列名由项目自己在 `results/.../README.md`
与本模块的协议模板里约定，跨 run 的汇总由 `summary_all.csv` 承担。

> 判据：一个约束值得强制，当且仅当违反它的代价是**信息永久丢失**。列名不一致的代价是
> 多写几行适配代码，可以恢复；配置不留档的代价是实验无法复现，不可恢复。

## 五、如何填 `[TODO: ...]`

模板里的 `[TODO: ...]` 分三类，填法不同：

| 类型 | 出现位置 | 怎么填 |
|------|---------|--------|
| **事实型** | 背景文档 §5 术语、§8 发现、§11 数据集路径 | 从代码/结果里查证后填。**查不到就保留 TODO**，不要写"大概" |
| **决策型** | 协议模板的判定标准、重复数、风险预案 | 跑实验**之前**填死。跑完再定等于事后编标准 |
| **叙事型** | 背景文档 §1 类比、§2 动机、§12 提示 | 写给人看，尽量具体到"谁在什么场景下会遇到" |

三条纪律：

- **不编数字**。虚构的数字比空白更危险——后续 AI 会把它当事实继续推理。
- **`{{PLACEHOLDER}}` 是机械替换**（项目名、日期、路径），`[TODO: ...]` 是需要判断的内容；
  不要用 `{{}}` 装需要思考的东西。
- **模板不删**：留着的 `[TODO: ...]` 是"这里还没想清楚"的可见信号。填不上就留着并写进
  `agent_memory/BOOT.md` 的待办，别悄悄删掉让文档显得完整。

## 六、与内核、cloud 模块的关系

- `core/agent_memory/` — 跨会话状态（BOOT / current_state / session_logs / plans）
- `core/CLAUDE.md.tmpl` — tier-0 协议；其中"文件放置原则"应与本模块的目录约定一致
- `modules/cloud/` — 云端协同工作流。**其归档流程引用本模块的 `docs/experiment_protocol.md`**
  作为"这次云端跑什么"的规格来源，因此该文件名与位置是接口，不要改。

一句话：内核负责"Agent 记得住"，本模块负责"结果说得清"。
