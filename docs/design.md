# 设计原理与开销核算

> 本文回答两个问题：**为什么这么分层**，以及**这套东西每次会话要花多少上下文**。
> 后者是设计约束，不是事后统计——本系统的很多取舍直接由它决定。

---

## 一、目标与约束

| 目标 | 含义 |
|---|---|
| 零交代启动 | 新会话的 Agent 不需要用户复述背景，就能知道项目是什么、做到哪了 |
| 跨会话连续 | 换会话、换机器、换模型，上下文都能重建 |
| 可校验 | 约定能用脚本查，而不是靠人记 |
| **省上下文** | 常驻成本要低到可以忽略 |

第四条是**约束**而非目标——它否掉了很多看起来更"完善"的方案（见第四节）。

---

## 二、上下文开销核算

### 每次会话的**常驻**成本

| 文件 | 行数 | 字节 | 何时加载 |
|---|---|---|---|
| `CLAUDE.md`（内核） | 78 | 3.4 KB | **自动，每次会话** |
| `AGENTS.md` | 与上者同源（略短） | — | 仅非 Claude Code 平台 |

**常驻成本只有一个文件，约 1.0k token 量级。** 这是刻意的：内核只写协议（去哪读），
不写知识（读到了什么）。

> **关于预算怎么定：** 内核的**目标**是 ~70 行，`check_conventions.py` 的**上限**设在 100 行、
> 涨到 85 行告警。把上限设得比目标宽，是因为——
> 源项目曾在文档里写「CLAUDE.md 保持在 ~40 行」，而它实际长到了 **128 行**。
> **一个没人能遵守的预算等于没有预算**：它先是失效，然后变成一句自相矛盾的说明。
> 所以这里的数字是「超过就该下沉了」的阈值，不是「理想状态」的口号。

### 按需加载的成本（不计入常驻）

| 文件 | 行数 | 何时读 |
|---|---|---|
| `agent_memory/BOOT.md` | 97 | 多数任务读这一层就够 |
| `agent_memory/current_state.md` | 125 | 需要完整细节时 |
| `agent_memory/session_logs/*.md` | 40–120 | 需要历史背景时，**只读最近一份** |
| `agent_memory/README.md` | 81 | 只需在**写**记忆前读一次 |

### 可选：SessionStart hook

若启用（**默认关闭**），每次会话额外注入 4–6 行 / 约 60–100 token。
判断是否值得：**如果你经常开短会话问零散问题，别开。** 详见 `modules/hooks/README.md`。

## 三、分层判据

一条信息该放哪一层，只问一个问题：

> **「每次会话都必须知道吗？」**

- 必须 → `CLAUDE.md`
- 多数任务需要 → `BOOT.md`
- 需要时查得到就行 → `current_state.md`
- 只是历史 → `session_logs/`

### 为什么必须分层

因为**上下文是有限的、且成本是线性的**。把 26 KB 的项目手册每次都塞进去，
既贵又会稀释真正重要的信息——模型在长上下文里的注意力分配是不均匀的，
塞进去的东西越多，关键约束越容易被忽略。

分层的本质是**把「检索」外包给 Agent 的决策**：Agent 判断需要什么，才去读什么。

## 四、关键取舍（明确不做什么）

这些是**被否掉的方案**，写下来是为了阻止后来者（包括未来的我自己）重新提议。

| 不做 | 理由 |
|---|---|
| ❌ 统一实验结果表的列名 | 这触及具体研究的数据结构。强行约定列名会让每个项目都要做适配层，**收益远小于成本**。缺的是「这个数字是哪次跑出来的」——那由 `run.json` 解决，与列名无关。 |
| ❌ 把 BOOT/current_state 合并成一个大文件 | 合并后就没有「多数任务读到一半就够」这个档位了，每次都得读全。 |
| ❌ 用 hook 强制注入完整上下文 | 完整上下文很贵。hook 只注入**指针**，不注入内容。 |
| ❌ 自动生成 session log 正文 | 日志的价值在于**判断**（哪些是稳健结论、哪些是条件相关的），不在格式。自动生成的流水账会稀释这一层。只提供模板，不提供生成器。 |
| ❌ 把所有模块默认全装 | 非科研项目会拿到一堆用不上的目录，反而增加噪音和「不知道该改哪」的成本。 |

## 五、与原系统的差异

本模板剥离自一套在真实科研项目中长期使用的系统。剥离时做了以下**有意**的改动：

| 改动 | 原系统状况 | 理由 |
|---|---|---|
| **`run.json` 实验溯源** | 全仓库无 run-id，变体只靠手工 `--tag` 区分，`history.json` 里查不出 epoch 数 | 一个 30-epoch 的跑和一个 10-epoch 的跑除文件夹名之外无法区分，这直接威胁可复现性 |
| **`check_conventions.py`** | 镜像规则、编号唯一性全是强约定但零校验，已出现重复编号与孤儿目录 | 靠人维护的约定必然衰减。能用脚本查的就不要靠人记 |
| **AGENTS.md 改为生成物** | 手工双写，实测两份入口文件三处互相矛盾 | 同一个事实写两遍必然漂移 |
| **`plans/` 生命周期字段** | 无 status 字段，一份早已失效的计划仍被标为「当前计划」 | 没有生命周期的计划目录最终会变成误导性文物 |
| **内核行数预算可校验** | 文档写着「保持在 ~40 行」，实际 128 行 | 无人检查的预算等于没有预算 |
| **hook 附开销核算** | 曾识别出 hook 路径但停在半路，未实施 | 缺的不是想法，是**明确的取舍判据**——现在写下来了 |

## 六、已知局限

1. **依赖 Agent 的自觉。** 除了 `check_conventions.py` 与可选 hook，绝大部分约定仍是
   「写下来让 Agent 遵守」。这是刻意的取舍——更强的强制需要更多机制，而机制本身也要维护。
2. **索引需要手工维护。** `current_state.md` 的会话日志索引必须每次手补。
   `check_conventions.py` 只能事后发现遗漏，不能替你补。
3. **`run.json` 需要每个实验脚本配合写入。** 提供 schema 和约定，但不提供自动注入——
   因为「这次实验的关键配置是什么」只有写脚本的人知道。
4. **中文语境优化。** 模板与文档是中文的，技术术语保留英文。移植到英文项目需要整体改写。
